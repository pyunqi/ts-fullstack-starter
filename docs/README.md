# docs

骨架自带两份文档：

- [new-project.md](new-project.md) —— 用 Claude Code 从这个骨架开新项目该怎么做
- [patterns/](patterns/) —— 没有默认装配、但需要时可以照着加的东西

**其余留给你的项目自己写。**

一个用得住的项目文档目录大致长这样，按需要建：

| 文件 | 回答什么 | 什么时候写 |
| --- | --- | --- |
| `design.md` | 系统在做什么、谁在用、有哪几条贯穿全局的规矩 | 第一个功能落地之前 |
| `deploy.md` | 按什么顺序部署、坏了怎么办 | 第一次真实部署**当天** |
| `product-logic.md` | 某条业务规则当初为什么这么定 | 开始出现「这个当初为什么这样」的时候 |
| `guide-*.md` | 使用者照着做的操作手册 | 交给非开发的人用之前 |

两条经验，都是拿时间换来的：

**部署手册的价值全在于它记的是真发生过的事。** 每次真实部署之后把踩到的坑
补进去 —— 「按什么顺序做」和「坏了怎么办」这两件事，事后回忆写不出来。

**操作手册要按版本存档。** 部署往往落后于开发分支十几个提交，
照着开发版的界面给使用者指路，会说到线上根本没有的按钮。
打 tag 时把当前版复制一份冻结（`guide-<版本>.md`），别在原地改。
