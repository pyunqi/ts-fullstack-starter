# 用 Claude Code 从这个骨架开一个新项目

这份文档讲的是**人和模型分别该做什么**。

核心是一句话：**这个骨架真正为 AI 协作准备的东西不是代码，是那五个守卫和
`CLAUDE.md`。** 它们把「这个项目的规矩」从一段需要每次复述的口头约定，
变成了模型自己能验证的东西 —— 你不必在每轮对话里重申「记得接进归档区」，
因为漏了的话 `pnpm check` 会当场告诉它。

---

## 一、先把仓库拉下来（人做，五分钟）

```bash
gh repo create my-new-app --private --clone
cd my-new-app
git remote add starter https://github.com/pyunqi/ts-fullstack-starter.git
git fetch starter && git reset --hard starter/main
git remote remove starter          # 不打算跟骨架同步就断掉
```

保留 `starter` 这个远程也可以 —— 以后骨架修了 bug，
`git cherry-pick` 那一个提交过来即可。但别指望长期 merge：
项目一旦长出自己的形状，两边就不再是同一棵树了。

然后：

```bash
nvm use && corepack enable pnpm && pnpm install
cp .env.example .env
pnpm db:generate && pnpm db:migrate && pnpm db:seed
pnpm run ci                        # 确认起点是绿的
```

**先跑通再交给模型。** 起点就是红的，模型会花掉整个第一轮去修环境问题，
而那些问题（Node 版本、pnpm 链接、缺 netlify CLI）你自己两分钟就能解决。

## 二、第一件事是改 `CLAUDE.md`（人做，十分钟）

`CLAUDE.md` 会在每次会话开始时自动进入模型的上下文。它现在写的是**骨架**，
不是你的项目 —— 不改的话，模型会一直以为自己在维护一个通用模版。

必须改的三处：

1. **开头那段「这是什么」** —— 换成你项目的一句话定位，
   以及**它刻意不做什么**。后者比前者有用得多：它决定了模型在遇到
   「要不要顺手加个 X」时的默认答案。
2. **「不可破的约束」** —— 删掉不适用的，加上你自己的。
   骨架列的那些（删除即归档、越权 404、不加冗余计数列）是从一个真实项目
   里来的，未必条条适合你。**留着一条你并不打算遵守的约束，
   比不写更糟** —— 模型会照做，然后你在 review 时反复推翻它。
3. **「发布现状」** —— 部署到哪、线上是哪一版、有没有连 CI。
   这一节的作用是防止模型照着本地代码给出线上根本不成立的操作建议。

> 别用 `/init` 重新生成 `CLAUDE.md`。那个命令是给没有说明的仓库用的，
> 它会扫代码总结出一份「这个项目有哪些目录」——而这份文件已有的价值
> 恰恰在于那些**从代码里读不出来**的东西：为什么这么定、漏了会怎样。

## 三、把「你的项目在做什么」写下来（人做，半小时）

在 `docs/design.md` 里回答三个问题：**系统在做什么、谁在用它、
有哪几条规矩是贯穿全局不能单点破例的**。

这半小时是整个流程里回报最高的。原因很实际：模型每一轮都会重新读这份文档，
而你不会每一轮都重新讲一遍。没有它，你会发现自己在第五轮对话里
第三次解释同一个业务规则。

写法参考 `docs/README.md` 里那张表。不必一次写全，
但**「贯穿全局的规矩」那一节要在第一个功能落地之前写**。

## 四、然后才开始让模型写代码

第一轮建议这样开：

> 读一遍 CLAUDE.md 和 docs/design.md，然后告诉我你打算怎么加「<某功能>」——
> 先给方案，别写代码。特别说清楚：要不要新表、新表要不要 archived_at、
> 有没有需要登记进 FAMILIES 的拼接键。

复杂功能先让它出方案（plan mode 或者直接要求「先给方案」）。
这个骨架里一个功能的实际扇出通常是十几个文件，其中大部分漏了会编译失败 ——
那些不用管；**要盯的是漏了不报错的那几处**，而它们恰好都是守卫在守的东西。

写完之后一律：

```bash
pnpm run ci
```

**让模型自己跑，自己修。** 守卫的报错信息是为「照着做就能修好」设计的 ——
每个脚本头部都写了这条规矩为什么存在，模型读完通常会改对，
而不是去改守卫绕过失败。

## 五、几条实测有用的约定

**守卫挂了，先读它说了什么，不要改守卫。**
这条值得直接写进你的 `CLAUDE.md`。守卫报错是设计的一部分，
改守卫让它闭嘴等于把安全带剪了。确实需要例外时，
两个脚本都留了正规的口子（`check-archive` 的 `PHYSICAL_DELETE`、
多租户那份文档里的 `scope-ok:`），**例外要有名有姓**。

**新依赖要先问。** 骨架的依赖是刻意少的：没有组件库、没有状态管理、
没有 ORM 之外的抽象。模型有很强的倾向去装一个包解决问题，
而每个包都要跟着升级、都可能在 Serverless 打包时炸掉
（`bcrypt` vs `bcryptjs` 那条坑就是这么来的）。

**改了界面就看截图。** 撑破的栏位、重复的标题、暗色下没定义的颜色，
typecheck 和测试全绿，只有看图才发现。让它用 `pnpm dev` 跑起来截个图。

**测试要有牙。** 让模型写完测试后把实现改坏一次，确认那条测试真的变红。
不做这一步的话，「碰巧通过」的测试会一直绿着，直到某天你依赖它却发现它从没生效。

**踩了坑就写进注释或 README。** 只留在 commit message 里等于没留 ——
下一轮对话的模型不会去翻 git log，但它每次都会读到代码里的注释。

## 六、`.claude/settings.json`

仓库里带了一份，作用是把这个项目里高频、只读或幂等的命令加进允许清单，
少一半权限确认弹窗：

```jsonc
{
  "permissions": {
    "allow": ["Bash(pnpm check)", "Bash(pnpm test)", "Bash(pnpm run ci)", "..."]
  }
}
```

**没有放进去的是写操作** —— `git commit`、`git push`、`pnpm db:migrate`、
任何 `rm`。这类命令每次都该由你点一下：迁移不可回滚，推送收不回来。

个人的、不该进 git 的授权记录会落在 `.claude/settings.local.json`，
那个文件已经在 `.gitignore` 里。

## 七、什么时候该回头改 `CLAUDE.md`

出现下面任何一种情况，就是该改的时候：

- 你在对话里**第二次**纠正同一件事 —— 说明那条规矩没写下来
- 模型反复问同一个问题 —— 说明入口文档里缺一条指路
- 某条约束你自己已经不遵守了 —— 立刻删掉，别留着让模型照做
- 加了新的守卫 —— 在那张表里补一行，说清它什么时候会挂

**一份和代码对不上的 `CLAUDE.md` 比没有更糟**：模型会完全信任它，
然后基于过期的前提做出一整串合理但错误的推断。
